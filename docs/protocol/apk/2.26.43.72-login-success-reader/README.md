## Selected login reader

[0ZJ.A13](login-reader.txt) calls `123.A08` for a node and explicitly branches
on web, success and failure. The web branch conditionally consumes another node;
it also throws for an unexpected or repeated web node. A missing node throws at
067e; a non-web/success/failure node reaches the unexpected-node throw at 064c.
The success branch checks the expected web prelude, parses supplied server time,
and reads props, abprops and mc_ep_version. This supports distinguishing an
unexpected initial reply from a failure stanza. It does not establish parity for
Rust's native web prelude, exception mapping, reconnect or persistent reservation
policy. The previous Rust outcome-classification fix remains locally tested.

At 01a0..01ae success reads `lid` with `0Tp.A0A(Jid.class, "lid")`, **not**
LidUserJid.class. When present, a DeviceJid is normalized through getUserJid
for comparison against `09F.Auj()`. A differing existing LID reports
lid-chatd-lid-mismatch and jumps back to the shared continuation (03da -> 01fc);
it does not immediately throw or skip that continuation. Later, only if the
`08Y.A17(0Yq.A04)` gate returns true, `09F.ChR` receives the original supplied
JID (0344..034a). Effective flag value, setter implementation, namespace policy
and full own-identity lifecycle remain **unknown in this trace**. This is not
permission to accept a different namespace in Rust.

## Getter is not a compliance rejection gate

[0Tp.A0A](jid-getter.txt) first uses an already typed attribute JID, otherwise
passes its string through `0Dd.A02`. A nonnull result calls isProtocolCompliant.
A false result logs an error and then rejoins conversion at 008a; it does not
return null or throw there. DeviceJid-specific conversion applies only when
DeviceJid.class was requested. Class.cast returns the result; a ClassCastException
is logged and returns null. This getter alone therefore cannot justify adding
ACK-specific numeric PN/LID grammar as a mandatory login rejection rule.
String parser details and upstream typed-attribute construction remain separate.
No numeric validation or acceptance claim is made for the complete native path.

No literal pn read occurs in this selected A13 method. That is a bounded search,
not proof that the app never handles PN at login. The two direct success helpers
are retained: [A18](success-key-helper.txt) conditionally decodes static_pq_key,
constructs KEMPublicKey and passes it to `143.CjR`; decode IllegalArgumentException
is reported and returns. [A0u](location-helper.txt), also called by failure,
handles a nonempty location shorter than 40 characters. Neither shown helper
reads pn. KEM consumer/configuration and location persistence internals were not
followed and are not newly claimed implemented in Rust.
