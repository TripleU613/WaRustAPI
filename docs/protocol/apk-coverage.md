# Retained APK evidence coverage

Updated 2026-11-04. Generated by `cargo run -p xtask -- apk-coverage` into
[apk-coverage.json](apk-coverage.json); `--check` fails when the committed report
is stale. Rerun it after adding or regenerating any bundle under
[apk/](apk/README.md), retained REA JSON/ownership sidecars, or library source file. CI enforces this
through the xtask test `committed_report_is_current`, which the change plan
selects for library sources, bundle `manifest.json`/`targets.json` files and the
report itself.

## What it measures

The existing `releases`, `topics` and `rust_files` sections still measure only
committed research bundles: each bundle's `manifest.json` (release and APK hash)
and `targets.json` (topic → class/method → Rust files). "Uncited" still means
*no retained bundle topic names this file*, not *no APK evidence exists for it*.

The separate `rea` section counts [retained REA envelopes](rea/) by APK hash,
release label and operation. It accepts both direct Evidence records and MCP
wrappers, requiring wrapper text and structured content to agree. It deduplicates
identical records by Evidence ID and refuses conflicting copies, malformed
identities, inconsistent APK/release labels and bundle-manifest hash mismatches.
Directory version labels are checked against package declarations where present;
for method-only evidence they remain labels corroborated by the available hash
association, not independently recovered package versions. The accounting does
not reauthenticate the content-derived Evidence ID cryptographically.

`rea.releases[].method_bodies` distinguishes complete exported bodies, unavailable
bodies and partial/unknown exports. `complete_export` requires nonempty source
text, a recognized `java`/`smali` representation, recorded class/method display
identity and nonnegative overload index, and the provider's available/complete
status. Missing, empty or malformed details remain `partial_or_unknown`; legacy
null DEX descriptors do not create descriptor-level coverage. A complete export
can be Java or smali; it is
not proof of source equivalence, a Rust port, complete call flow or runtime parity.
Package summaries, class inventories and reference searches are record counts
only. The legacy certificate-parser note is explicitly listed in `rea.excluded`
because it is not an REA Evidence record. Bundle topics and REA records can overlap;
adding those counts or dividing them by APK class counts would invent a completion
percentage. Classes cited only in comments/prose and unexported code remain outside
the machine-readable accounting.

## Explicit REA ownership

REA ownership is opt-in and separate from bundle citation counts. A release
directory may contain `ownership.json` mapping retained IDs to existing Rust
source paths and the exact APK hash:

```json
{
  "evidence": {
    "ev_aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa": {
      "apk_sha256": "887a6f94f6614791cfa845fe0b9990c064326d8b89cd71d81e817fc9fd530c2e",
      "rust_files": ["crates/whatsapp-api/src/registration/wire.rs"]
    }
  }
}
```

The example ID is illustrative. Use actual retained IDs. Sidecars with unknown
IDs, conflicting declarations, hash mismatches, empty ownership lists, non-Rust
paths, missing files or path traversal are refused. Duplicate paths within one
record count once. `rea.records_with_explicit_ownership` counts mapped distinct
records; `rea.releases[].rust_files` counts mapped records per Rust file.
Prose, directory names and obfuscated class names never supply ownership implicitly.
This is traceability, not verification that the file implements every behavior.

## How to extend coverage

With the exact APK available (including through the repository's published
research asset; see [APK procedure](apk-analysis.md#obtaining-the-apk)):

1. export the pinned 2.26.36.75 core topics with `apk-research-bundle` and a
   recipe, then `apk-research-diff` against the 37.70 core bundle;
2. for uncited files that implement traced behaviour, add their topics to the
   relevant recipe so `rust_files` names them;
3. for a new release, `apk-research-remap` the 37.71 recipes, export, diff and
   rerun this report.

4. retain focused REA Evidence records and optional explicit ownership sidecars,
   then rerun `apk-coverage`; keep raw APKs and bulk decompilation outside Git.
